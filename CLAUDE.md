# auto_despachos_silogtran

API que un LLM usa para confirmar/despachar solicitudes de transporte en **Silogtran** (TMS PRADO/PHP, sin API oficial) mediante scraping HTTP. Despliegue en **Vercel** (team `grachos-projects`, plan gratuito).

## Reglas de trabajo
- Explicaciones en **español**; código, identificadores y comentarios en **inglés**.
- Incrementos pequeños; **pedir aprobación antes de implementar cada incremento**.
- Repo **público**: secretos solo en variables de entorno. Mantener `.env.example` sin valores. Nunca commitear `.env`, cookies, HTML capturado con datos reales ni logs con credenciales.
- Fase 2 (no ahora): mapear el motivo de rechazo del RNDC.

## Base técnica
- Reutilizar el cliente de `grachos/apis_legalizacion_silogtran` (`src/silogtran.js`, `src/session.js`): login + centro de costo + reto AWS WAF con Chromium, cookie jar, cola serializada, `pradoCallback`, `formFields`.
- Centro de costo: siempre se escoge el primero disponible (sin variable de entorno).
- En Vercel: `@sparticuz/chromium` + `puppeteer-core` solo para resolver el WAF; el resto es HTTP plano.
- Cookies/sesión persistidas en **Supabase** para no relogear en cada invocación.
- Lock por solicitud (una solicitud a la vez).

## Flujo de despacho (pantalla `Despacho.Solicitudtransporte.Visor_105`, validado manualmente)
1. Consultar en `Despacho.Solicitudtransporte.Buscar` (campo `soltra_codigo`; con un resultado abre el formulario). Leer `soltra_contenedor` (SI/NO), origen y destino.
2. Visor: "Quitar Todos" (limpia pendientes) → postback Confirmar en la fila solicitud+item (EventTarget `ctl0$MainModule$visor$ctlN$ctl36`) → postback "Continuar confirmacion".
3. Marcar `porConfirmar$ctl0$genera_manifiesto` (postback; Orden de cargue y Remesa se marcan y bloquean solas).
4. Vehículo: CAutoComplete `vehiculo_codigo_seleccion_activo` con la placa → ID en `$IDHidden` → botón `buscar_activo` ("Seleccionar", postback). Silogtran llena `trailer_codigo`, `tercero_codigo_conductor`, clase, carrocería, tipo operación. Sin resultados → `VEHICLE_NOT_ACTIVE`; varios → `AMBIGUOUS_OPTION`.
5. Ruta: CAutoComplete `ruta_codigo` con `ORIGEN%DESTINO`; elegir coincidencia exacta `ORIGEN - DESTINO`. Al seleccionar se calcula el Anticipo. Sin resultados → `ROUTE_NOT_FOUND`.
6. Fechas (America/Bogota): `fecha_salida`/`hora_salida` = ahora (`yyyy-MM-dd` / `HH:mm:ss`); `fecha_limiteentrega`/`hora_limiteentrega` = salida + 5 días; `fecha_limitecumplido` = limiteentrega + 5 días; `soltra_volumengalontanqueado` = 0.
7. `tipmanrndc_codigo`: opcional. **Default por regla de negocio**: si Ciudad Origen = Ciudad Destino del ítem (sin mayúsculas, tildes ni espacios sobrantes) → 6 (VIAJE MUNICIPAL O URBANO); si son distintas → 1 (MANIFIESTO GENERAL). Un `tipoManifiesto` explícito siempre tiene prioridad. Acepta código o texto parcial sin tildes: 1 general, 2 varios viajes en el día, 3 multiparada, 4 ida y regreso, 5 viaje vacío, 6 municipal o urbano, 7 varios viajes municipales. Ambiguo → `AMBIGUOUS_OPTION` con opciones.
8. Anticipo: `"total"` (valor calculado por Silogtran) o `"cero"` (Anticipo=0 y disparar callback `ctl32`). Si total, pestaña Pago Anticipos: `tipegr_codigo`=TRANSFERENCIA POR ARCHIVO, `ValorPago`=anticipo, `banco_codigo` autocomplete `BANCOLOMBIA%PROPIOS` (ID 3) → Adicionar.
9. Pestaña Observaciones Documentos: `itemobservaciones_ordenCompra`, `itemobservaciones_Ordencargue`, `itemobservaciones_Remesa` (default "NA"; Remesa obligatoria, oculta a la derecha); `remesa_fechacompromiso`/`horacompromiso` (cita cargue) y `remesa_citadescarguefecha`/`hora` (cita descargue) **obligatorias**, vienen del usuario; tiempos pactados 2 h 0 min en cargue y descargue → Adicionar.
10. Si `soltra_contenedor`=SI: pestaña Contenedores, `itemremesacontenedor_ContenedorCodigo` (autocomplete por número) + `itemremesacontenedor_IteremconNumerobl` obligatorios → Adicionar. Faltan → `CONTAINER_REQUIRED`; no existe → `CONTAINER_NOT_FOUND`. Si NO, vacía. Pestañas Equipos y Auxiliar no se llenan.
11. Grabar = postback `ctl0$MainModule$Generar` (incluye `grabar_uuid`). Éxito: "El registro ha sido guardado!" + tabla "Documentos Generados" (Orden de Cargue, Remesa, Manifiesto, Transferencia). Otros mensajes (ej. "Respuesta Plataforma Monitor ... 500") → `warnings`.
12. Estado RNDC: `GET index.php?page=Despacho.Manifiesto_003.Home_111&manifiesto_codigo=N` → texto de `#ctl0_MainModule_manifiesto_numero` con formato `consecutivo - radicado / Fecha Hora fecha`. Radicado presente = migró; vacío = "Sin migrar al Ministerio".

## Contrato de la API
Consumidor: un LLM. Errores: `{ ok:false, code:"FIXED_CODE", message:"<español>" }`. Auth: header `x-api-key`.

- `POST /api/solicitudes/:numero/preparar`
  Body: `{ placa, citaCargue{fecha,hora}, citaDescargue{fecha,hora}, tipoManifiesto?, ordenCompra?, observacionOrdenCargue?, observacionRemesa?, contenedor?, bl? }`
  Llena todo **sin grabar**; devuelve resumen (vehículo, trailer, conductor, ruta, fechas, anticipo sugerido, requiereContenedor) + `token`.
- `POST /api/solicitudes/:numero/confirmar`
  Body: `{ token, anticipo: "total"|"cero" }`. Rehace el llenado, verifica que el anticipo no cambió (`ANTICIPO_CHANGED`), graba y responde:
  `{ ok, status:"DISPATCHED"|"DISPATCHED_NOT_MIGRATED", message:"Se despachó a satisfacción. Remesa X, Manifiesto Y. Radicado Ministerio Z | Sin migrar al Ministerio.", documents{ordenCargue,remesa,manifiesto,transferencia}, rndc{migrated,radicado,fechaHora}, warnings[] }`

Códigos de error conocidos: `VEHICLE_NOT_ACTIVE`, `AMBIGUOUS_OPTION`, `ROUTE_NOT_FOUND`, `CONTAINER_REQUIRED`, `CONTAINER_NOT_FOUND`, `ANTICIPO_CHANGED` (+ los de infraestructura que se definan: auth, login, WAF, lock).

- La app tendrá usuarios independientes de Silogtran. En la web (Vercel) cada persona registra su usuario y contraseña de Silog; con eso se le entrega un **código de un solo uso, con expiración**, para vincular su número de **WhatsApp Business API (Meta)**.
- Los despachos se lanzan desde WhatsApp con una IA conversacional que pregunta los valores en lenguaje natural; también puede recibir **una tabla** con varios despachos, interpretarla, crearlos y devolver los resultados.
- Credenciales Silog por usuario: guardadas en Supabase **cifradas** (AES-GCM, clave maestra solo en variable de entorno), descifradas solo en memoria al abrir la sesión, nunca en logs ni respuestas. Viajan solo por HTTPS.
- Sesión Silogtran por usuario (`silog_session.id` = id de usuario; hoy `default` = "usuario cero" con `SILOG_USER`/`SILOG_PASSWORD`).
- Token de `preparar` ligado al usuario. Lock por usuario+solicitud guardado en Supabase (Vercel no comparte memoria).
- Auth: token por usuario; `API_KEY` queda como clave de servicio entre el bot de WhatsApp y esta API.
- Lotes: despachos largos (Vercel gratis corta a 60 s) → trabajos asíncronos en cola y resultado por WhatsApp. `preparar`/`confirmar` deben ser funciones independientes de la petición HTTP.
- La **confirmación humana** (resumen + anticipo) se mantiene siempre antes de grabar, también en lotes.

## `confirmar` (3d) — protecciones
- Token de un solo uso (`jti`): tabla `silog_confirmaciones` (`PROCESSING` → `DONE` | `FAILED` | `UNKNOWN`). Mismo token ya `DONE` → devuelve el resultado guardado con `repeated: true` (no vuelve a grabar). `FAILED` (no se grabó) puede reintentarse; `UNKNOWN` (el guardado pudo haber ocurrido) exige verificar a mano y un token nuevo. Una fila `PROCESSING` de más de 3 min pasa a `UNKNOWN`.
- Lock por solicitud: índice único parcial sobre `numero` donde `status='PROCESSING'` → `SOLICITUD_LOCKED` (409).
- `ANTICIPO_CHANGED` si el anticipo recalculado difiere del token. El estado `DONE` se guarda **antes** de consultar el RNDC. Si el RNDC no se puede leer: `DISPATCHED` con advertencia.
- Errores: `SAVE_REJECTED` (Silogtran respondió sin guardar), `SAVE_RESULT_UNKNOWN`, `CONFIRMATION_IN_PROGRESS`, `CONFIRMATION_UNKNOWN`, `TOKEN_INVALID`, `TOKEN_EXPIRED`, `BANK_NOT_FOUND`, `ANTICIPO_PAGO_NOT_ADDED`.

## M1 implementado (usuarios, credenciales cifradas e invitaciones)
- Tablas `app_users` e `invitaciones` (migración 003; RLS sin políticas, solo service key). `app_users.silog_user_key` (minúsculas) es único: un usuario de Silog no puede estar en dos usuarios de la app.
- `src/crypto.js`: AES-256-GCM, formato `v1:iv:tag:ct`, **AAD = id del usuario** (un cifrado copiado a otra fila no descifra). `ENCRYPTION_KEY` = 64 hex; si falta o es inválida, falla antes de tocar Silogtran. `getCredentials(userId)` descifra solo en memoria (se usa desde M4).
- `POST /api/admin/invitaciones` (`x-api-key` = `ADMIN_KEY`, distinta de `API_KEY`): `{ nombre }` crea usuario + invitación, `{ userId }` re-invita (revoca los links previos sin usar). Devuelve el link una sola vez (`https://<host>/invitacion?t=<token>`; también funciona `/invitacion/<token>`); en BD solo se guarda el hash SHA-256. Vigencia: 2 h.
- `POST /api/invitaciones/:token/login` `{ usuario, clave }`: (1) valida el link y responde `INVITATION_NOT_FOUND|USED|EXPIRED|LOCKED` **antes** de tocar Silogtran; (2) reserva un intento con compare-and-set atómico (máx. 5); (3) login real en Silogtran con un cliente **nuevo** (no toca la sesión del usuario cero; solo reutiliza cookies `aws-waf*` para evitar Chromium); (4) credenciales malas → 401 `LOGIN_REJECTED` con `intentosRestantes`; error de infraestructura (WAF, red) → **devuelve el intento**; (5) éxito → consume el link de forma atómica, guarda la contraseña cifrada y las cookies bajo el id del usuario y emite la cookie de sesión (`sid`, HttpOnly, Secure, SameSite=Lax, 30 min). `SILOG_USER_ALREADY_LINKED` (409) si ese usuario de Silog ya está vinculado a otra persona.
- `typ` en los tokens firmados: `preparar` vs `session` no son intercambiables (`confirmar` rechaza cualquier token que no sea `preparar`). `src/http/session.js`: `setSessionCookie` / `readSession`.
- Errores nuevos: `CONFIG_INVALID` (variable presente pero con formato inválido), `INVITATION_*`, `LOGIN_REJECTED`, `LOGIN_NOT_SUPPORTED` (contraseña por cambiar o 2FA), `SILOG_USER_ALREADY_LINKED`, `USER_NOT_FOUND`, `USER_NOT_ACTIVE`, `DECRYPT_FAILED`.

## M4 implementado (despachar con la sesión de cada usuario)
- **Actor**: todo despacho se ejecuta como un usuario (`userId`) o como el usuario cero (`null`, credenciales de entorno). `src/silogtran/userSession.js`: `openActorSession` descifra las credenciales **solo en memoria**, reutiliza la sesión guardada del usuario (`silog_session.id` = id) y solo relogea si hace falta. Las funciones del servicio (`src/dispatch/service.js`: `consultSolicitud`, `prepareDispatch`; y `confirmDispatch` en `src/confirmar.js`) no dependen de HTTP: el asistente (M5) las llamará directamente. Las rutas HTTP son envoltorios delgados; con la `API_KEY` de servicio aceptan `usuario` (id o usuario de Silog; body o query) para actuar como ese usuario, y sin él usan el usuario cero.
- **Token ligado al dueño**: `preparar` siempre escribe `uid` (explícitamente `null` para el usuario cero). `confirmar` usa la sesión del dueño del token; si además llega `usuario`, debe coincidir (`TOKEN_USER_MISMATCH`, 403). Se vuelve a comprobar que el usuario siga activo al confirmar.
- **Bloqueo por sesión de Silogtran** (`store/locks.js`, tabla `silog_locks`; clave = id de usuario o `default`; token de dueño; TTL 90 s; un bloqueo vencido se puede retomar): lo toman **todas** las operaciones que usan una cookie jar (consulta, preparar, confirmar y `rndc-actualizar`, que usa el usuario cero). Si está ocupado → `USER_BUSY` (409). Motivo: dos flujos sobre la misma jar se pisan (ambos relogean y cambia PHPSESSID, o "Quitar Todos" borra el pendiente del otro). En `confirmar` el bloqueo se toma **antes** del claim, así un usuario ocupado no deja un claim colgado.
- **Orden en `confirmar`**: verificar token → resolver/validar actor (solo BD: `RELINK_REQUIRED` / `USER_NOT_ACTIVE` sin tocar Silogtran) → bloqueo → claim → abrir sesión → llenar → grabar. **Corregido un fallo previo**: abrir la sesión estaba fuera del `try`; si fallaba (WAF, red, credenciales) el claim quedaba `PROCESSING` y pasaba a `UNKNOWN` ("verifica en Silogtran") aunque no se hubiera grabado nada. Ahora queda `FAILED` (reintentable) y la limpieza usa `client?.`.
- **Credenciales inválidas**: solo un fallo "duro" de login (`Login failed: <texto del panel>`, cambio de contraseña obligatorio o 2FA) marca al usuario como `NEEDS_RELINK`, **una sola vez y de forma atómica** (`update … where status='ACTIVE' returning`); solo quien lo marcó avisa por WhatsApp. El mensaje genérico "rejected the login" y cualquier error de infraestructura **no** lo marcan. Desde ahí todas las llamadas se detienen en la comprobación de estado **sin intentar login** (protege la cuenta de Silogtran de bloqueos). Re-invitar al usuario (login exitoso) lo reactiva y borra la marca.
- **Estado sin tocar la restricción**: `NEEDS_RELINK` se guarda como `status='DISABLED'` + `relink_required=true` (migración 007 solo aditiva); `getUser`/`findUserByRef`/`getLinkByPhone`/admin lo exponen como `NEEDS_RELINK` (el panel lo muestra "Requiere link nuevo" y cuenta los usuarios afectados; el bot tiene mensaje propio).
- **Migración 007 (aplicada 2026-11-04)**: `alter table public.app_users add column if not exists relink_required boolean not null default false;` + tabla `silog_locks (key text primary key, token text not null, expires_at timestamptz not null)` con RLS activado y sin políticas.
- Errores nuevos: `USER_BUSY`, `RELINK_REQUIRED`, `CREDENTIALS_INVALID`, `TOKEN_USER_MISMATCH`, `USER_NOT_FOUND`.
- Pendiente (M5): aviso de WhatsApp fuera de la ventana de 24 h de Meta requiere una **plantilla aprobada**; hoy el aviso de "contraseña inválida" es texto libre y puede fallar sin afectar la respuesta HTTP (solo se registra el código del error).

## M5 implementado (asistente de IA por WhatsApp, OpenAI)
- **El modelo no puede grabar.** Solo tiene dos herramientas (`consultar_solicitud`, `preparar_despacho`, esquemas estrictos, `parallel_tool_calls:false`, máx. 4 llamadas por turno); una herramienta inventada (p. ej. `confirmar_despacho`) devuelve `UNKNOWN_TOOL`. **Confirmar ocurre solo al pulsar un botón interactivo que envió el servidor** (`Anticipo total` / `Anticipo cero` / `Cancelar`; solo `Confirmar`/`Cancelar` si el anticipo sugerido es 0). Un "sí" escrito o hablado solo reenvía los botones; un "no" suelto no cancela (puede responder otra pregunta); "cancelar" sí.
- **Token fuera del modelo**: tras `preparar`, el token vive en `ia_pendientes` (migración 008) y el id del pendiente va en el id del botón (`ctot|ccero|canc:<uuid>`). Al pulsar: `claimPending` atómico (dueño = usuario del teléfono, estado `PENDING`, no vencido, y es el más reciente: crear uno nuevo deja los anteriores `SUPERSEDED`); estados `PENDING → PROCESSING → USED | CANCELLED | SUPERSEDED`; un fallo antes de grabar devuelve a `PENDING` (se puede volver a pulsar), `ANTICIPO_CHANGED`/token vencido → `SUPERSEDED`, resultado dudoso o rechazado → `USED`. La idempotencia por token de `confirmar` cubre el doble toque.
- **El resumen lo redacta el código** (`src/ai/summary.js`) desde el resumen estructurado que devolvió Silogtran (placa realmente encontrada, conductor, ruta, citas con **día de la semana**, anticipo): lo que se confirma es la realidad de Silogtran, no la paráfrasis del modelo. En voz, primero un eco determinista «🎙️ Entendí: «…»».
- **Voz**: descarga en 2 pasos con Bearer (máx. 5 MB) → `gpt-4o-mini-transcribe` (es, temperatura 0, prompt de vocabulario del dominio, sin `;codecs=opus`, archivo `.ogg`). Nunca se registran transcripciones ni textos de mensajes (solo códigos de error).
- **Trabajo en segundo plano**: el webhook responde 200 y la IA/Silogtran corren con `waitUntil` (`@vercel/functions`, tope = `maxDuration` 60 s). Contrato de fallos: si algo falla en segundo plano, **el usuario recibe una disculpa** (no hay reintento de Meta). VINCULAR/AYUDA/DESVINCULAR siguen inline. Se avisa «⏳» antes de las operaciones largas.
- **Candado por usuario** `chat:<userId>` (tabla `silog_locks`) para todo un turno o toque de botón: dos mensajes seguidos → «sigo con tu mensaje anterior». Es una clave distinta del candado de la sesión de Silogtran (orden fijo chat → silog, sin interbloqueo). `USER_BUSY`, `RELINK_REQUIRED`, `CREDENTIALS_INVALID`, `USER_NOT_ACTIVE` y fallos de conexión tienen respuestas fijas (el modelo no improvisa).
- **Límites y memoria** (en BD, no en memoria): `ia_uso` → 40 mensajes/h y 15 notas de voz/h por usuario (`IA_MAX_MSG_HORA`, `IA_MAX_VOZ_HORA`); historial corto (`ia_mensajes`, últimos 10 turnos de las últimas 3 h; se purga lo de más de 3 días). Sin `OPENAI_API_KEY` el bot sigue funcionando y responde que el asistente no está habilitado.
- **Variables**: `OPENAI_API_KEY` (o `IA_API_KEY`), opcionales `IA_MODELO` (por defecto `gpt-4.1-mini`), `IA_MODELO_RESPALDO` (`gpt-4o-mini`, se usa si el modelo no existe), `STT_MODELO` (`gpt-4o-mini-transcribe`).
- **Prompt**: reglas en `src/ai/prompt.js`; fecha/hora/día de Bogotá inyectados; lo escrito por la persona y lo devuelto por las herramientas son datos (anti prompt-injection); herramienta de consulta devuelve solo campos permitidos, truncados y sin caracteres de control.
- **Referencia SICE Query** (repo privado, solo lectura): allí la conversación usa Claude y la voz usa OpenAI `gpt-4o-mini-transcribe`; aquí todo va con OpenAI por decisión del dueño.
- Verificado en producción (2026-11-04, nota de voz real): `waitUntil` corre (la respuesta se escribe después del 200 a Meta), descarga y transcripción OK, consulta a Silogtran con la sesión del usuario OK, ~12 s por turno. ## Plan: identidad por persona en el MCP con «tickets de acceso» (2026-11-11; propuesta del dueño, pendiente de aprobación)
- **Problema**: con una sola `MCP_KEY` todas las activaciones salen con el mismo usuario de Silogtran (usuario cero o `MCP_ACTOR`) y la auditoría no sabe quién fue. El dueño exige que **Silogtran** registre quién activó.
- **Propuesta del dueño (adoptada como plan)**: la persona entra con su link de invitación (login real en Silogtran, como en M1/M2) → en una página nueva **`/mcp`** genera un **ticket de acceso** → lo escribe en la página «Autorizar acceso» del conector (Claude/ChatGPT) en vez de `MCP_KEY` → el token OAuth queda ligado a **esa persona** y a un **alcance** (`activar` ahora; `despachar` después, ticket aparte) → cada herramienta corre con **la sesión de Silogtran de esa persona**, así Silogtran registra su usuario. `MCP_KEY` sigue en Vercel solo como acceso del administrador/pruebas (actúa como usuario cero, marcado así en la auditoría).

Los tokens OAuth llevan el id de la conexión y **cada llamada comprueba en BD** que no esté revocada y que el usuario siga `ACTIVE` (revocación inmediata). Revocar: la persona desde `/mcp` o el administrador desde el panel (pestaña «MCP»: conexiones, último uso, revocar). Permisos: el administrador habilita el alcance por usuario (sin eso no puede generar tickets). Máx. 3 conexiones activas por alcance y persona (Claude + ChatGPT + celular).

## Links de invitación independientes por propósito (2026-11-11, IMPLEMENTADO; decisión del dueño)
- **Regla**: cada link de invitación es de **un solo propósito** y no se mezclan: `whatsapp` (vincular el teléfono y despachar por el chat), `activar` (activaciones de **vehículos y proveedores** por IA/MCP) y, más adelante, `despachar` (M6; hoy **no se puede emitir**). Una persona puede tener uno de cada uno; cada uno es de un solo uso, 2 h, 5 intentos.
- **Datos**: columna `invitaciones.scope` (migración 013, aplicada; `default 'whatsapp'`, así los links y filas anteriores siguen siendo de WhatsApp). Re-invitar revoca solo los links sin usar **del mismo propósito** (los de otro propósito siguen vigentes). `POST /api/admin/invitaciones { nombre | userId, scope?: 'whatsapp'|'activar' }` (el panel: selector «Para qué es el link» en la pestaña Invitaciones; el resultado indica el tipo).
- **Sesión por propósito** (`src/http/session.js`): el login con el link emite una cookie **propia del propósito** (`sid` para WhatsApp —nombre histórico; las cookies sin `sc` cuentan como WhatsApp—, `sid_activar` para activaciones, `sid_<scope>` en general) con `{uid, sc}`; `requireSession(req, scope)` exige la cookie de **ese** propósito. Así `/vincular` (+ `codigo`, `estado`) solo abre con el link de WhatsApp y `/mcp` (+ `mcp-ticket`, `mcp-conexiones`, `mcp-revocar`) solo con el de activaciones; no hay enlaces cruzados entre ambas páginas.
- **El link es la autorización**: al entrar con un link de `activar` se concede automáticamente el alcance MCP `activar` (`setScope`), sin paso de «Habilitar» del administrador (la pestaña MCP del panel ahora solo permite **Quitar**, que corta conexiones y tickets al instante, y lista conexiones). Un link de WhatsApp no concede nada.
- **Un link nunca re-vincula a otra persona**: si la persona ya tiene usuario de Silogtran y escribe otro distinto → `SILOG_USER_MISMATCH` (409) **antes** de gastar un intento ni tocar Silogtran.
- **Flujo web**: `GET /api/invitaciones/:token/login` (sin gastar intento) devuelve `{ scope }` para que `/invitacion` muestre el título y la descripción del propósito; el `POST` devuelve `{ scope, siguiente }` (`/vincular` o `/mcp`) y fija la cookie del propósito. Pruebas locales (`tinv.mjs`): cookies no intercambiables, alcance concedido solo por el link de activaciones, mismatch sin gastar intento, links sin `scope` = WhatsApp.
- Para despachar por MCP (M6) bastará añadir `despachar` a `INVITE_SCOPES`/`SCOPES` y a `SCOPE_PAGE` (misma infraestructura de tickets y conexiones).
